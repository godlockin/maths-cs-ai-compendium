# 题 1：客服机器人系统

## 1.1 题目陈述

> "**设计一个客服机器人系统**. 以电商客服为例，帮用户查询订单、退换货、咨询商品信息。 要求能理解用户意图、提取关键信息 (订单号/商品名)，并自动生成回复。 当机器人无法处理时，转人工客服."

这是 NLP 面试中最经典的"综合题"——它把意图分类 (Intent Classification)、槽位填充 (Slot Filling)、对话状态管理 (Dialogue State Management，简称对话状态跟踪)、回复生成 (Response Generation) 全部串起来。 而且，面试官会追问"从规则到 BERT 再到 LLM 怎么演进"——这是考察候选人是否经历过 NLP 技术栈升级。

## 1.3 Step 1 — Clarify (0:00-0:05)

满分话术 (向面试官确认):

> "**业务范围**：电商客服，核心场景——订单查询、退换货、商品咨询、投诉。 这些是高频场景，覆盖 80% 用户请求。
>
> **离线/在线**：在线实时，用户在等，期望 < 500ms 出回复。 离线批量复盘用于模型更新。
>
> **技术栈**：用户说中文，混有口语化表达 (如"我的快递咋还没到")、错别字、中英混合。 需要中文 NLP 全栈能力。
>
> **转人工条件**：机器人置信度低 (< 0.7)、用户情绪激烈 (愤怒/投诉)、用户要求"转人工". 这 3 个条件触发转人工。
>
> **冷启动**：新业务上线，没有历史对话数据。 先用规则引擎 + 人工标注对话模板，积累 1 万条后再上模型."

## 1.4 Step 2 — Metrics (0:05-0:10)

客服机器人有 5 层指标，面试时至少答出前 3 层:

### 1.4.1 业务层指标

**首次接触解决率 (First Contact Resolution, FCR)** — 用户一次对话就解决需求，不重复提问的概率。 行业电商客服 FCR 目标 70-80%.

**客户满意度 (Customer Satisfaction, CSAT)** — 对话结束后用户打分 (1-5 分), 4 分以上算满意。 目标 ≥ 4.2.

**转人工率** — 机器人处理的对话中，最终转到人工客服的比例。 越低越好。 行业目标 15-25%.

### 1.4.2 模型层指标

**意图分类准确率**：多分类，覆盖 10-20 个意图。 准确率 ≥ 95%.

**槽位填充 F1**：实体抽取 F1 分数。 订单号/商品名/日期等，F1 ≥ 90%.

**回复 BLEU/Rouge-L**：生成回复与标准回复的相似度。 辅助指标，不高。

### 1.4.3 系统层指标

**P50/P99 延迟**：上线前 < 500ms P99，上线后 < 1s P99.

**吞吐量**：每秒处理请求数 (QPS). 单机 ≥ 100 QPS.

### 1.6.2 意图分类：规则 → BERT → LLM

**第一代 — 规则引擎 (Rule-based)**:

```python
# 规则引擎意图分类 (关键词匹配 + 正则)
import re

class RuleIntentClassifier:
    """基于规则的首轮意图分类, 冷启动用."""
    
    def __init__(self):
        self.rules = {
            "查订单": [
                r"(查|看|找|查查|看看).*(订单|快递|物流|包裹|到哪)",
                r"(订单|快递|物流|包裹).*(号|编号|号码)",
                r"我的.*(订单|快递|物流|包裹)",
            ],
            "退货": [
                r"(退|退货|退款|退换)",
                r"(不想要|不满意|有问题|坏了)",
                r"7天.*退货",
            ],
            "投诉": [
                r"(投诉|举报|差评|给差评|投诉到)",
                r"(客服|态度|服务).*(差|不好|恶劣)",
                r"(315|12315|消费者协会)",
            ],
            "商品咨询": [
                r"(多大|多少钱|什么颜色|尺寸|材质|能用)",
                r"(质量|好不好|怎么样|评价|推荐)",
                r"(搭配|配什么|适合)",
            ],
            "转人工": [
                r"(人工|转人工|找人工|客服|在线客服|人工客服)",
                r"(转|接).*(人工|客服)",
            ],
        }
    
    def predict(self, text: str) -> tuple:
        """返回 (意图, 置信度)."""
        for intent, patterns in self.rules.items():
            for pattern in patterns:
                if re.search(pattern, text):
                    return intent, 0.9  # 规则命中, 置信度高
        return "未知", 0.0
```

**缺点**：规则引擎覆盖有限，用户说"我昨天买的手机怎么还没到"就匹配不到"查订单". 冷启动时勉强可用，但一旦积累 1 万 + 标注数据，必须上模型。

**第二代 — BERT 微调**:

```python
# BERT 意图分类 (PyTorch)
from transformers import BertModel, BertTokenizer
import torch
import torch.nn as nn

class IntentClassifier(nn.Module):
    """BERT 微调意图分类, 支持 10-20 个电商意图."""
    
    def __init__(self, model_name="bert-base-chinese", num_intents=12):
        super().__init__()
        self.bert = BertModel.from_pretrained(model_name)
        self.dropout = nn.Dropout(0.1)
        self.classifier = nn.Linear(self.bert.config.hidden_size, num_intents)
    
    def forward(self, input_ids, attention_mask):
        outputs = self.bert(input_ids=input_ids, attention_mask=attention_mask)
        # 用 [CLS] token 的表示做分类
        pooled = outputs.last_hidden_state[:, 0, :]  # [CLS] token
        pooled = self.dropout(pooled)
        logits = self.classifier(pooled)
        return logits

# 训练: 每轮对话用户首句作为输入, 意图标签作为输出
# 数据: 1 万+ 人工标注对话
# 推理: 单条 < 30ms (T4 GPU), INT8 量化后 < 10ms

# 评估: 意图准确率 ≥ 95%, 混淆矩阵重点看"查订单"和"退货"之间的混淆
```

**BERT 的不可替代优势**：用户说"我昨天买的手机怎么还没到"——BERT 能理解"查订单"意图，因为"还没到"隐含了"物流查询"语义。 这是规则引擎做不到的。

**第三代 — LLM 少样本**:

LLM 时代，意图分类可以用 In-context Learning (ICL) 做:

```python
# LLM 少样本意图分类 (Prompt 模板)
INTENT_PROMPT = """你是一个电商客服意图分类器. 请判断用户的意图属于以下哪一类:
- 查订单: 查询物流、订单状态、快递信息
- 退货: 退货、退款、退换货
- 投诉: 投诉商家、客服投诉
- 商品咨询: 咨询商品信息、价格、规格
- 转人工: 要求转人工客服
- 其他

用户: {user_message}
意图:"""

# 调用 LLM 获取回复, 解析意图
# 优点: 零标注, 灵活, 支持任意意图
# 缺点: 延迟高 (500ms-2s), 成本高, 不稳定
```

**演进路径总结**:

| 方案 | 准确率 | 延迟 | 标注成本 | 维护成本 | 适用阶段 |
|---|---|---|---|---|---|
| 规则引擎 | 70-80% | < 5ms | 低 | 高 | 冷启动 |
| BERT 微调 | 95%+ | < 30ms | 中 (1 万+) | 低 | 上线后 |
| LLM 少样本 | 90-95% | 500ms-2s | 低 | 低 | 新意图探索 |

**面试官追问**: "BERT 和 LLM 意图分类你应该选哪个?"

✅ 答：上线初期用 LLM 少样本快速验证，用 LLM 标注数据蒸馏到 BERT 模型，线上用 BERT 推理 (低成本低延迟), LLM 只做兜底和冷启动。 这是**蒸馏 (distillation)** 的典型应用。

### 1.6.3 槽位填充 (Slot Filling)

槽位填充本质是**命名实体识别 (Named Entity Recognition, NER)**，但对话场景的 NER 更依赖上下文:

```python
# BERT 槽位填充 (NER 序列标注)
from transformers import BertForTokenClassification

class SlotFiller(nn.Module):
    """BERT 序列标注, 提取槽位值."""
    
    def __init__(self, model_name="bert-base-chinese", num_labels=9):
        # 标签: O(非实体), B-order(订单号开始), I-order(订单号内部),
        #       B-prd(商品名开始), I-prd(商品名内部),
        #       B-date(日期开始), I-date(日期内部),
        #       B-price, I-price
        super().__init__()
        self.bert = BertForTokenClassification.from_pretrained(
            model_name, num_labels=num_labels
        )
    
    def forward(self, input_ids, attention_mask, labels=None):
        outputs = self.bert(
            input_ids=input_ids,
            attention_mask=attention_mask,
            labels=labels,  # 训练时提供标签
        )
        return outputs  # loss, logits, ...

# 推理: 输入"查一下订单 12345 到哪里了"
# 输出: "查一下订单 [B-order]1[I-order]2[I-order]3[I-order]4[I-order]5 到哪里了"
# 解析: 订单号 = "12345"

# 关键: 槽位值需要和对话状态管理联动
# 例如用户说"帮我查一下", 上一轮已收集到"订单号=12345",
# 这一轮不需要用户重复说订单号
```

### 1.6.4 对话状态管理 (Dialogue State Management)

对话状态管理 (DST) 负责跟踪多轮对话中**已收集到什么信息、还缺什么信息**:

```python
# 对话状态管理 (Dialogue State Tracker)
class DialogueStateTracker:
    """跟踪对话状态, 决定下一步动作."""
    
    def __init__(self):
        self.state = {
            "intent": None,        # 当前意图
            "slots": {},           # 已收集的槽位
            "required_slots": {},  # 当前意图所需槽位
            "turn": 0,             # 当前轮次
            "history": [],         # 对话历史
            "handoff_needed": False,  # 是否需要转人工
        }
        
        # 每个意图需要的槽位
        self.intent_requirements = {
            "查订单": {"order_id": "订单号"},
            "退货": {"order_id": "订单号", "reason": "退货原因"},
            "投诉": {"order_id": "订单号", "description": "投诉描述"},
            "商品咨询": {"product_name": "商品名"},
        }
    
    def update(self, intent, slots):
        """更新对话状态."""
        self.state["turn"] += 1
        self.state["intent"] = intent or self.state["intent"]
        self.state["slots"].update(slots)
        self.state["required_slots"] = self.intent_requirements.get(
            self.state["intent"], {}
        )
    
    def get_missing_slots(self):
        """返回还缺哪些槽位."""
        required = set(self.state["required_slots"].keys())
        collected = set(self.state["slots"].keys())
        missing = required - collected
        return {k: v for k, v in self.state["required_slots"].items()
                if k in missing}
    
    def next_action(self):
        """决定下一步动作: 追问 / 执行 / 转人工."""
        if self.state["turn"] > 5:
            # 5 轮还没解决, 转人工
            return "handoff", "不好意思, 已为您转接人工客服"
        
        missing = self.get_missing_slots()
        if missing:
            # 追问缺失的槽位
            slot_name = list(missing.values())[0]
            return "ask_slot", f"请问您的{slot_name}是?"
        
        # 全部收集完成, 执行业务查询
        return "execute", None
```

### 1.6.5 回复生成 (Response Generation)

回复生成有 3 种方案，按复杂度递增:

**1. 模板回复** (最简单，90% 场景够用):

```python
# 模板回复
TEMPLATES = {
    "查订单_成功": "好的, 查到您的订单 {order_id} 当前状态为: {status}. 预计 {eta} 送达.",
    "查订单_失败": "查询订单 {order_id} 失败, 请确认订单号是否正确.",
    "退货_成功": "已为您提交退货申请, 退货单号 {return_id}. 快递员将上门取件.",
    "退货_失败": "抱歉, 订单 {order_id} 已超出退货时效 (7 天), 无法办理退货.",
    "投诉_登记": "已记录您的投诉, 客服专员将在 24 小时内联系您.",
    "商品咨询_回复": "{product_name} 当前价格为 ¥{price}, 库存 {stock} 件.",
}
```

**2. 检索式回复** (BERT 语义匹配，从知识库找最相似 QA):

```python
# 检索式回复: 用 BERT 做语义匹配
from sentence_transformers import SentenceTransformer, util

class RetrievalResponse:
    """从知识库检索最相似的 QA 对."""
    
    def __init__(self, knowledge_base):
        self.encoder = SentenceTransformer("paraphrase-multilingual-MiniLM-L12-v2")
        # 预编码知识库所有问题
        self.kb_questions = [item["question"] for item in knowledge_base]
        self.kb_answers = [item["answer"] for item in knowledge_base]
        self.kb_embeddings = self.encoder.encode(
            self.kb_questions, convert_to_tensor=True
        )
    
    def retrieve(self, query, top_k=1):
        """检索最相似的问题."""
        query_emb = self.encoder.encode(query, convert_to_tensor=True)
        scores = util.cos_sim(query_emb, self.kb_embeddings)[0]
        top_idx = scores.argsort(descending=True)[:top_k]
        return [
            {"question": self.kb_questions[i],
             "answer": self.kb_answers[i],
             "score": float(scores[i])}
            for i in top_idx
        ]
```

### 1.6.6 转人工 (Handoff) 策略

转人工是客服机器人的"安全阀". 面试官特别关注：候选人是否知道**不是所有问题都该机器人回答**.

```python
# 转人工判定逻辑
class HandoffDecision:
    """什么时候转人工."""
    
    @staticmethod
    def should_handoff(intent_result, slot_result, dialog_state, user_sentiment):
        """转人工条件."""
        reasons = []
        
        # 条件 1: 意图置信度低
        if intent_result.confidence < 0.7:
            reasons.append("意图不明确")
        
        # 条件 2: 用户情绪激烈
        if user_sentiment < -0.5:
            reasons.append("用户情绪负面")
        
        # 条件 3: 用户明确要求转人工
        if intent_result.intent == "转人工":
            reasons.append("用户要求转人工")
        
        # 条件 4: 多轮未解决
        if dialog_state.turn > 5:
            reasons.append("超过 5 轮未解决")
        
        # 条件 5: 敏感场景 (投诉/纠纷)
        if intent_result.intent == "投诉":
            reasons.append("投诉场景需人工")
        
        # 条件 6: 模型不确定 (LLM 复审)
        if intent_result.intent == "其他":
            reasons.append("模型无法识别意图")
        
        return len(reasons) > 0, reasons
```

**面试官追问**: "怎么处理冷启动?"

✅ 答：新业务上线，没有历史对话。 先用规则引擎 (关键词) 跑 1 周，收集 1 万 + 对话。 然后人工标注 2 千条，训练 BERT 意图分类。 上线后，用 LLM 做兜底——当 BERT 置信度 < 0.8 时，走 LLM 判断。 LLM 的判断结果自动回流做"伪标注"，积累到 5 千条后重新训练 BERT. 这就是**自训练 (self-training) 循环**.

## 2.4 Step 2 — Metrics (0:05-0:10)

### 2.4.1 延迟指标

**TTFT (Time to First Token，首 token 延迟)**：从用户发送请求到收到第一个 token 的时间。 目标：P50 < 500ms, P99 < 2s.

**TPOT (Time per Output Token，每 token 延迟)**：生成每个后续 token 的时间。 目标：< 50ms/token.

**E2E 延迟**：完整回复延迟。 目标：100 token 回复 < 5s.

### 2.4.2 吞吐指标

**吞吐量 (Throughput)**：每秒生成 token 数。 单机 A100 80GB 70B 模型，约 1000-2000 tokens/s.

**QPS (Queries Per Second)**：每秒请求数。 目标：1000 QPS.

### 2.4.3 安全指标

**安全拦截率**：系统拦截的违规内容占全部违规内容的比例。 目标：> 99%.

**误拦截率**：正常内容被误拦截的比例。 目标：< 0.1%.

**越狱检测率**：检测到越狱尝试的比例。 目标：> 95%.

### 2.5.2 LLM Serving 核心技术

**问题**: 70B 模型，FP16，一张 A100 80GB 装不下。 必须用**张量并行 (Tensor Parallelism, TP)** 把模型切到多卡上。

**张量并行 (TP)**：把每层矩阵切分到多张 GPU 上。 例如，4 卡 TP，每张卡只存 1/4 的权重。 前向传播时，每张卡计算自己的部分，用 all-reduce 通信汇总结果。

**流水线并行 (PP)**：把层分段，每段在不同 GPU 上。 例如，70B 模型 80 层，4 卡 PP，每卡 20 层。

**TP 通信量数学**:

对于 Transformer 层，前向传播需要一次 all-reduce 同步注意力输出，一次 all-reduce 同步 FFN 输出。 每次 all-reduce 的通信量:

$$\text{Comm}_{\text{TP}} = 2 \times (4 \times d_{\text{model}} \times \text{rank} \times 2 \text{ bytes})$$

其中 $d_{\text{model}}$ 是隐藏维度，rank 是 TP 卡数。 70B 模型 $d_{\text{model}} \approx 8192$, 4 卡 TP，每层通信量约 524 KB. 80 层则约 42 MB 每 token.

**KV 缓存 (KV cache) 显存公式**:

$$
\text{KV cache memory} = 2 \times 2 \times n_{\text{layers}} \times d_{\text{model}} \times n_{\text{heads}} \times \text{seq\_len} \times 2 \text{ bytes}
$$

其中第 1 个 2 是 K 和 V，第 2 个 2 是每头的维度。 实际计算:

$$M_{\text{kv}} = 2 \times n_{\text{layers}} \times d_{\text{model}} \times n_{\text{heads}} \times \text{seq\_len} \times \text{dtype\_bytes}$$

用 70B 模型举例：$n_{\text{layers}} = 80$, $d_{\text{model}} = 8192$, $n_{\text{heads}} = 64$, seq_len = 4096, FP16 (2 bytes):

$$M_{\text{kv}} = 2 \times 80 \times 8192 \times 64 \times 4096 \times 2 = 2 \times 80 \times 8192 \times 64 \times 4096 \times 2 = 2 \times 80 \times 8192 \times 64 \times 4096 \times 2$$

逐步计算:
$$= 2 \times 80 \times 8192 \times 64 \times 4096 \times 2$$
$$= 2 \times 80 \times 8192 \times 64 \times 8192$$
$$= 2 \times 80 \times 8192 \times 524288$$
$$= 2 \times 80 \times 4,294,967,296$$
$$= 2 \times 343,597,383,680$$
$$= 687,194,767,360 \text{ bytes} \approx 640 \text{ GB}$$

**640 GB 显存** 才能存下 70B 模型单条 4096 token 会话的 KV 缓存！这解释了为什么 LLM serving 的核心瓶颈是**显存**，而不是算力。

**解决方案**: 
- **PagedAttention** (vLLM)：把 KV 缓存分页，像虚拟内存一样管理，减少碎片，提升 2-4 倍批大小
- **KV cache 共享**：前缀相同的请求共享 KV 缓存 (Prompt Cache)
- **KV cache 量化**: INT8 量化 KV 缓存，省 50% 显存

### 2.5.3 连续批处理 (Continuous Batching)

**传统批处理**：等一批请求全部完成后，一起处理。 短请求必须等长请求，浪费 GPU 算力。

**连续批处理 (continuous batching)**：每个请求独立处理，请求完成后立即加入新请求。 理论上，连续批处理比传统批处理提升 2-4 倍吞吐。

$$
\text{Throughput}_{\text{continuous}} = \frac{\sum_{i=1}^{N} \text{seq\_len}_i}{\max_i \text{seq\_len}_i \times \text{batch\_size}} \times \text{Throughput}_{\text{single}}
$$

在短请求多的场景，连续批处理优势更明显——因为长请求不会拖慢短请求。

| 快速原型 / 中小规模 | vLLM | 最爱，部署简单，兼容 HuggingFace 模型 |
| 多轮对话 / 中等规模 | SGLang | 预填充/解码分离，多轮对话效率高 |

| 研究 / 快速迭代 | vLLM | 灵活，支持新模型快 |

### 2.5.5 安全层 (Safety Layer)

安全层是 LLM 系统的"门卫"，分输入和输出两层:

**输入安全层 (Pre-filter)**:

```python
# 输入安全层: 内容审核 + 越狱检测
class InputSafetyLayer:
    """过滤用户输入, 防止有害内容进入 LLM."""
    
    def __init__(self):
        self.content_moderation = load_moderation_model()
        self.jailbreak_detector = load_jailbreak_model()
        self.pii_detector = load_pii_model()  # PII: 个人信息
    
    def check(self, user_message: str) -> dict:
        """返回审核结果."""
        result = {
            "is_safe": True,
            "reasons": [],
            "action": "pass",  # pass / block / warn
        }
        
        # 1. 内容审核 (暴力/色情/政治敏感)
        mod_result = self.content_moderation.predict(user_message)
        if mod_result.is_unsafe:
            result["is_safe"] = False
            result["reasons"].append(f"内容违规: {mod_result.category}")
            result["action"] = "block"
        
        # 2. 越狱检测
        jailbreak_check = self.jailbreak_detector.detect(user_message)
        if jailbreak_check.is_attack:
            result["is_safe"] = False
            result["reasons"].append(f"越狱尝试: {jailbreak_check.technique}")
            result["action"] = "block"
        
        # 3. PII 脱敏 (不阻止, 但脱敏)
        pii_result = self.pii_detector.detect(user_message)
        if pii_result.has_pii:
            result["reasons"].append(f"检测到PII: {pii_result.types}")
            # 脱敏处理, 不阻止
            result["masked_message"] = self.pii_detector.mask(user_message)
        
        return result
```

**输出安全层 (Post-filter)**:

```python
# 输出安全层: 过滤有害回复
class OutputSafetyLayer:
    """过滤 LLM 生成的回复, 防止有害内容输出."""
    
    def __init__(self):
        self.content_moderation = load_moderation_model()
        self.quality_filter = load_quality_model()
    
    def check(self, output_text: str, input_text: str) -> dict:
        """返回审核结果."""
        result = {
            "is_safe": True,
            "reasons": [],
            "action": "pass",
        }
        
        # 1. 内容审核
        mod_result = self.content_moderation.predict(output_text)
        if mod_result.is_unsafe:
            result["is_safe"] = False
            result["reasons"].append(f"输出违规: {mod_result.category}")
            result["action"] = "block"
            result["replacement"] = "抱歉, 我无法生成该内容."
        
        # 2. 质量过滤 (重复/无意义/空洞)
        quality = self.quality_filter.score(output_text)
        if quality < 0.3:
            result["warnings"].append("回复质量低, 建议重新生成")
        
        # 3. 事实性检查 (简单版)
        # 实际场景用 RAG 或外部知识库做事实校验
        
        return result
```

## 3.4 Step 2 — Metrics (0:05-0:10)

### 3.4.1 检索指标

**P@K (Precision at K)**：检索返回的前 K 个结果中，相关文档的比例。 目标：P@5 ≥ 0.8.

**Recall@K**：检索返回的前 K 个结果中，覆盖了多少相关文档。 目标：Recall@10 ≥ 0.9.

**MRR (Mean Reciprocal Rank)**：第一个相关结果排名的倒数均值。 目标：MRR ≥ 0.9.

### 3.4.2 RAGAS 指标

检索增强生成评估 (Retrieval-Augmented Generation Assessment, RAGAS) 是 Shahul Es 等人 2023 年提出的 RAG 评估框架，核心有 3 个指标:

**Faithfulness (忠实度)**：生成的回答是否完全基于检索到的上下文，不包含幻觉。

$$\text{Faithfulness} = \frac{|\text{claims supported by context}|}{|\text{total claims in answer}|}$$

其中 claims 是回答中的独立陈述。 例如"公司年假是 15 天，需要工作满 1 年"包含 2 个 claims，如果两个都能在检索到的上下文中找到，Faithfulness = 1.0.

**Answer Relevance (回答相关性)**：回答是否回答了用户的问题。

**Context Precision (上下文精确率)**：检索到的上下文中，有多少是真正相关的。

RAGAS 的总体分:

$$RAGAS = \frac{\text{Faithfulness} + \text{Answer Relevance} + \text{Context Precision}}{3}$$

### 3.5.2 Chunking 策略

Chunking 是 RAG 最容易被忽视但影响最大的环节。 切得太大，检索精度下降；切得太小，上下文不完整。

**三种 Chunking 策略**:

```python
# 三种 Chunking 策略

# 1. Fixed-size Chunking (固定大小切分)
# 简单, 但可能切断完整段落
def fixed_chunk(text, chunk_size=512, overlap=50):
    tokens = tokenize(text)
    chunks = []
    for i in range(0, len(tokens), chunk_size - overlap):
        chunk = tokens[i:i + chunk_size]
        chunks.append(detokenize(chunk))
    return chunks

# 2. Semantic Chunking (语义切分)
# 按段落/句子边界切分, 保持语义完整
def semantic_chunk(text):
    # 按段句切分, 保持段落完整
    paragraphs = text.split("\n\n")
    chunks = []
    for para in paragraphs:
        if len(tokenize(para)) > 512:
            # 长段落按句子切分
            sentences = split_sentences(para)
            for sent in sentences:
                chunks.append(sent)
        else:
            chunks.append(para)
    return chunks

# 3. Hierarchical Chunking (层级切分) — 推荐方案
# 父文档 + 子段落 + 摘要, 检索时先匹配摘要, 再返回父文档
class HierarchicalChunker:
    """层级切分: 文档 → 摘要 → 段落 → 句子."""
    
    def __init__(self, llm):
        self.llm = llm  # 用 LLM 生成摘要
    
    def chunk(self, document):
        # 1. 生成文档摘要 (用 LLM)
        summary = self.llm.generate(f"总结以下文档: {document[:2000]}")
        
        # 2. 按段落切分
        paragraphs = document.split("\n\n")
        
        # 3. 按句子切分长段落
        segments = []
        for para in paragraphs:
            if len(para) > 500:
                segments.extend(split_sentences(para))
            else:
                segments.append(para)
        
        return {
            "summary": summary,
            "segments": segments,
            "document_id": hash(document),
        }
```

**推荐方案**：层级切分 (Hierarchical). 检索时先用摘要匹配，找到最相关的文档，再在文档内按段落检索。 既保证检索精度，又保证上下文完整。

### 3.6.2 稠密检索 (Dense Retrieval)

**Dense Passage Retrieval (DPR, Karpukhin 2020)** 是稠密检索的代表工作。 核心思想：用双编码器 (dual-encoder) 分别编码问题和段落，用余弦相似度匹配。

**DPR 的损失函数** (对比学习):

$$\mathcal{L} = -\log \frac{e^{\text{sim}(q, p^+)}}{e^{\text{sim}(q, p^+)} + \sum_{j=1}^{N} e^{\text{sim}(q, p_j^-)}}$$

其中 $q$ 是问题编码，$p^+$ 是正例段落编码，$p_j^-$ 是负例段落编码。 目标是让正例的相似度远大于所有负例。

```python
# DPR 检索器
from sentence_transformers import SentenceTransformer

class DenseRetriever:
    """稠密检索: 用 BGE 双编码器."""
    
    def __init__(self, model_name="BAAI/bge-large-zh-v1.5"):
        self.encoder = SentenceTransformer(model_name)
        self.documents = []      # 文档列表
        self.embeddings = None   # 预计算文档嵌入
    
    def index_documents(self, documents):
        """批量索引文档."""
        self.documents = documents
        texts = [doc["text"] for doc in documents]
        # 批量编码, 3000 文档/秒 (A100)
        self.embeddings = self.encoder.encode(
            texts, convert_to_tensor=True, show_progress_bar=True
        )
    
    def retrieve(self, query, top_k=20):
        """检索最相似的文档."""
        query_emb = self.encoder.encode(query, convert_to_tensor=True)
        # 余弦相似度
        scores = (self.embeddings @ query_emb.T).squeeze()
        top_idx = scores.argsort(descending=True)[:top_k]
        return [
            {"doc": self.documents[i], "score": float(scores[i])}
            for i in top_idx
        ]
```

### 3.6.3 稀疏检索 (Sparse Retrieval)

**BM25** 是经典的稀疏检索算法，基于关键词匹配。 适合：专有名词 (公司名/政策名/产品名)，精准匹配场景。

**密集检索 vs 稀疏检索对比**:

| 维度 | Dense (稠密) | Sparse (稀疏) |
|---|---|---|
| 原理 | 语义匹配 | 关键词匹配 |
| 优点 | 理解同义词，语义相关 | 精确匹配，专有名词 |
| 缺点 | 语义漂移，专有名词弱 | 同义词不匹配 |
| 资源 | 需要 GPU，存储量大 | 只需 CPU，存储小 |
| 适用 | 开放域 QA，语义检索 | 专有名词，精确匹配 |

### 3.6.4 混合检索 (Hybrid Retrieval)

**混合检索 = Dense + Sparse，加权融合**:

```python
# 混合检索: Dense + Sparse 加权融合
class HybridRetriever:
    """混合检索: Dense 语义 + Sparse 关键词."""
    
    def __init__(self, dense_weight=0.7):
        self.dense_retriever = DenseRetriever()
        self.sparse_retriever = BM25Retriever()
        self.dense_weight = dense_weight
    
    def retrieve(self, query, top_k=100):
        """混合检索, 返回 Top-K 个候选."""
        # 1. Dense 检索: 语义匹配
        dense_results = self.dense_retriever.retrieve(query, top_k * 2)
        
        # 2. Sparse 检索: 关键词匹配
        sparse_results = self.sparse_retriever.retrieve(query, top_k * 2)
        
        # 3. 分数归一化 (Min-Max)
        def normalize(results):
            scores = [r["score"] for r in results]
            min_s, max_s = min(scores), max(scores)
            for r in results:
                r["score"] = (r["score"] - min_s) / (max_s - min_s + 1e-8)
            return results
        
        dense_results = normalize(dense_results)
        sparse_results = normalize(sparse_results)
        
        # 4. 加权融合
        combined = {}
        for r in dense_results:
            combined[r["doc"]["id"]] = {
                "doc": r["doc"],
                "score": self.dense_weight * r["score"],
            }
        for r in sparse_results:
            doc_id = r["doc"]["id"]
            if doc_id in combined:
                combined[doc_id]["score"] += (1 - self.dense_weight) * r["score"]
            else:
                combined[doc_id] = {
                    "doc": r["doc"],
                    "score": (1 - self.dense_weight) * r["score"],
                }
        
        # 5. 排序取 Top-K
        results = sorted(combined.values(), key=lambda x: x["score"], reverse=True)
        return results[:top_k]
```

### 3.6.5 Re-ranking (Cross-encoder)

检索阶段用双编码器 (Dense + Sparse) 快速找到 Top-100 候选，排序阶段用**交叉编码器 (Cross-encoder)** 精排。

**Cross-encoder: monoBERT (Nogueira & Cho, 2019)**:

```python
# Cross-encoder Re-ranking
from sentence_transformers import CrossEncoder

class ReRanker:
    """Cross-encoder 精排: 输入 (query, document), 输出相关度分数."""
    
    def __init__(self, model_name="BAAI/bge-reranker-v2-m3"):
        # 中文 Cross-encoder 重排序模型
        self.model = CrossEncoder(model_name)
    
    def rerank(self, query, candidates, top_k=5):
        """从 Top-100 候选中选择 Top-5."""
        # 生成 (query, doc) 对
        pairs = [(query, c["doc"]["text"]) for c in candidates]
        
        # Cross-encoder 打分
        scores = self.model.predict(pairs)
        
        # 按分数排序
        for i, c in enumerate(candidates):
            c["rerank_score"] = float(scores[i])
        
        candidates.sort(key=lambda x: x["rerank_score"], reverse=True)
        return candidates[:top_k]
```

**Cross-encoder 的分数公式**:

对于每个 (query, document) 对，Cross-encoder 输出一个相关度分数:

$$s(q, d) = \text{sigmoid}(W \cdot \text{BERT}([CLS] q [SEP] d [SEP]))$$

其中 $W$ 是线性分类层的权重。 交叉编码器比双编码器精度高 5-10%，但速度慢 10-100 倍，所以只在 Top-100 候选上做精排。

def build_context(documents):
    """构建上下文文本."""
    contexts = []
    for i, doc in enumerate(documents):
        source = doc["doc"].get("source", f"文档{i+1}")

        contexts.append(f"[{source}]\n{text}")

### 3.7.2 忠实度 (Faithfulness) 控制

RAG 的核心挑战是**让 LLM 忠实于检索到的上下文，而不是凭记忆生成**. 控制方法:

```python
# Faithfulness 控制: 让 LLM 只基于上下文回答
class FaithfulnessController:
    """控制 LLM 生成忠实于上下文的回答."""
    
    def __init__(self, llm):
        self.llm = llm
    
    def generate(self, question, contexts):
        """生成忠实回复."""
        # 1. 构建 prompt (强制要求基于上下文)
        prompt = self._build_prompt(question, contexts)
        
        # 2. 生成初始回答
        response = self.llm.generate(prompt)
        
        # 3. Faithfulness 检查 (用少样本)
        check_prompt = f"""判断以下回答中的每个陈述是否能在上下文中找到支持.

回答: {response}

上下文: {contexts}

请输出每个陈述的分析:
1. "..." — 支持 / 不支持 / 部分支持
2. "..." — 支持 / 不支持 / 部分支持
..."""

        check_result = self.llm.generate(check_prompt)
        
        # 4. 如果有不支持的陈述, 重新生成或删除
        if "不支持" in check_result:
            # 重新生成, 更严格约束
            prompt = self._build_prompt(question, contexts, strict=True)
            response = self.llm.generate(prompt)
        
        return response
```

## 3.9 Prompt Cache / Semantic Cache

RAG 系统的一个优化点是**缓存**——相同问题重复出现时，不需要重新检索和生成:

```python
# 语义缓存 (Semantic Cache)
class SemanticCache:
    """语义缓存: 相似问题直接返回缓存答案."""
    
    def __init__(self, embedding_model, similarity_threshold=0.95):
        self.encoder = SentenceTransformer(embedding_model)
        self.threshold = similarity_threshold
        self.cache = {}  # query_embedding -> answer
        self.cache_embeddings = []
    
    def get(self, query):
        """检查缓存中是否有相似问题."""
        query_emb = self.encoder.encode(query, convert_to_tensor=True)
        
        if len(self.cache_embeddings) == 0:
            return None
        
        # 余弦相似度搜索
        scores = (self.cache_embeddings @ query_emb.T).squeeze()
        if len(scores.shape) == 0:
            scores = scores.unsqueeze(0)
        
        max_score = scores.max()
        if max_score > self.threshold:
            idx = scores.argmax().item()
            return list(self.cache.values())[idx]
        
        return None
    
    def put(self, query, answer):
        """存入缓存."""
        query_emb = self.encoder.encode(query, convert_to_tensor=True)
        self.cache[query] = answer
        self.cache_embeddings.append(query_emb)
```

## 📌 本节要点

- **3 道题覆盖对话系统核心**：客服机器人 (传统 NLP 基本功) + ChatGPT 类通用对话 (LLM Serving 系统) + RAG (检索增强生成)，层层递进。

- **转人工 6 条件**：置信度低 / 情绪负面 / 用户要求 / 多轮 / 投诉 / 未知意图，这是客服机器人安全阀。
- **KV Cache 显存公式**: $M_{\text{kv}} = 2 \times n_{\text{layers}} \times d_{\text{model}} \times n_{\text{heads}} \times \text{seq\_len} \times 2$, 70B 模型 4096 token 需约 640 GB 显存。
- **LLM Serving 全链路 7 层**: LB → Rate Limiter → Router → Prompt Preprocessor → Safety Input → LLM Server → Safety Output.
- **vLLM / SGLang / TensorRT-LLM 三选一**: vLLM (快速原型) / SGLang (多轮对话) / TRT-LLM (高吞吐生产).
- **RAG 检索 → 排序 → 生成**：混合检索 (Dense + Sparse) → Cross-encoder Re-ranking → 上下文注入 + 引用。
- **RAGAS 评估 3 指标**: Faithfulness (忠实度) + Answer Relevance (回答相关性) + Context Precision (上下文精确率).
- **DPR 对比学习损失**: $\mathcal{L} = -\log \frac{e^{\text{sim}(q, p^+)}}{e^{\text{sim}(q, p^+)} + \sum_{j=1}^{N} e^{\text{sim}(q, p_j^-)}}$，让正例远大于负例。
- **连续批处理提升吞吐 2-4 倍**：每个请求独立处理，完成即加入新请求，不等待长请求。
