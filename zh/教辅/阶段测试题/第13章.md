### 1. 🟢【L1 记忆】命题逻辑中，德摩根律 $\neg(p \wedge q)$ 等价于：

A. $\neg p \wedge \neg q$
B. $\neg p \vee \neg q$
C. $p \vee q$
D. $\neg p \to \neg q$

---

**答案**: B

**解析**: 否定一个“与”要分别否定两部分并换成“或”：$\neg(p \wedge q) \equiv \neg p \vee \neg q$。编程里对应 `!(a && b)` 等价于 `(!a || !b)`。

**来源**: 01. 离散数学 §命题逻辑

### 2. 🟡【L2 理解】关于 P 与 NP 的关系，下列说法正确的是：

A. $P = NP$ 已经被证明
B. P 与 NP 互不相交
C. $P \subseteq NP$，但 $P$ 是否等于 $NP$ 仍是开放问题
D. NP 问题都是不可判定问题

---

**答案**: C

## 三、简答题（6 × 5 = 30 分）

### 16. 🟡【L2 理解】用自己的话说明停机问题为什么不可判定，并指出它对工程实践的一个实际后果。

---

**答案**: 假设存在停机检测器 $H(P, x)$ 能判断任意程序 $P$ 在输入 $x$ 上是否停机。构造程序 $D$：它对 $(D, D)$ 跑 $H$，然后做相反的事——$H$ 说停机就无限循环，$H$ 说死循环就停机。于是 $H(D, D)$ 无论输出什么都自相矛盾，故 $H$ 不可能存在（图灵，1936，反证法）。

工程后果（任举其一即可）：不存在完美的死锁检测器、完美的病毒扫描器或对所有输入都最优的优化编译器——它们都等价于一般地解决停机问题；真实工具只能做启发式与近似，在常见情形有效，不能保证对所有输入正确。

**解析**: 关键得分点：反证构造 $D$、自指矛盾、“数学上不可能而非技术局限”、工程工具只能启发式近似。

**来源**: 01. 离散数学 §可计算性

### 17. 🟡【L2 理解】解释“带宽瓶颈”（存储层级意义上的内存墙）的成因，以及它为什么让 LLM 推理成为 memory-bound 任务。

---

**答案**: 处理器算力的增长速度远快于内存带宽与访存速度的改善，层级中最快的存储（寄存器、L1）容量极小，大容量 DRAM 延迟在 50-100 ns 量级，GPU 常常“算得比数据喂得快”。

LLM 推理时每生成一个 token 都要把模型权重逐层读一遍：70B 模型 FP16 权重约 140 GB（$70\times10^9 \times 2$ 字节；INT8 量化后约 70 GB），单批请求下计算量不足以摊薄这次读取，耗时由权重加载主导，因此是 memory-bound。正文给出的缓解方向：顺序访问利用空间局部性、加大批大小摊薄访存延迟、混合精度/量化（fp16、INT8/INT4）让有效带宽翻倍、计算与 I/O 重叠。

**解析**: 得分点：算力与带宽增速差、延迟层级数字、推理逐 token 读权重、至少两条缓解手段。

**来源**: 02. 计算机架构 §存储层级

### 18. 🟡【L2 理解】进程与线程的核心区别是什么？各举一个适合使用它的场景。

---

**答案**: 进程拥有独立的地址空间（代码、堆、文件描述符互不共享），一个进程崩溃不直接影响其它进程，进程间通信（IPC）成本高；线程存活在进程内部，同一进程的线程共享堆与打开的文件，只各自保留独立的栈与寄存器上下文，线程切换更轻量，但共享可变数据需要互斥锁等同步原语防竞态。

场景（各一）：浏览器用多进程隔离不同标签页，一个页面崩溃不拖垮整个浏览器；Web 服务器用线程池并发处理大量请求，线程间共享连接池与缓存、切换成本低。

**解析**: 得分点：地址空间独立 vs 共享、隔离性与开销的权衡、两个场景与理由对应正确。

**来源**: 03. 操作系统 §进程 / §线程

### 20. 🟡【L2 理解】区分并发（concurrency）与并行（parallelism），并解释 Python 的 GIL 为什么让 CPU 密集任务转而使用多进程；3.13/3.14 在这方面有什么变化？

---

**答案**: 并发是“管理”多个任务，任务通过交替推进，单核上也能制造同时执行的假象；并行是多个任务在多个执行单元上同一瞬间真正同时执行，需要多核硬件。

Python 的全局解释器锁（GIL）使同一时刻只有一个线程执行 Python 字节码，多线程无法做真正的 CPU 并行，只适合 I/O 并发；CPU 密集任务因此用多进程（每进程独立解释器）绕开 GIL。变化：Python 3.13（2024-10）引入实验性 free-threaded（无 GIL）构建；按 PEP 779，3.14（2025-10）起该构建获官方支持（仍为可选构建、非默认），单线程开销约 5-10%，真正的多线程并行已可落地。

**解析**: 得分点：交替 vs 同时、GIL 限制字节码并行、多进程绕开、3.13 实验/3.14 官方支持的时间线。

**来源**: 04. 并发与并行 §并发 vs 并行

### 21. 🟡【L2 理解】比较三种内存管理路线：手动管理、垃圾回收、Rust 所有权。各自的代价是什么？

---

**答案**:

- 手动管理（C/C++，malloc/free）：给出原始速度与硬件级控制力，但靠人保证配对，易出现释放后使用、重复释放、内存泄漏。
- 垃圾回收（Java/Go/Python）：运行时从根出发追踪可达对象、自动回收不可达内存，程序员不调 free；代价是 GC 停顿与运行时开销（现代 ZGC、Go 并发 GC 已把停顿压到亚毫秒级），且无法消除引用泄漏。
- Rust 所有权 + 借用检查器：在编译期就杜绝释放后使用、重复释放、数据竞争与悬垂指针，没有 GC、没有运行时开销；代价是借用检查器学习曲线陡峭。

**解析**: 三条路线各 1.5 分左右，须同时写出收益与代价；只背名称不给分。

**来源**: 05. 编程语言 §内存管理

## 四、编程题（2 × 10 = 20 分）

### 22. 🟡【L3 应用】写一个 Python 真值表生成器：给定命题变量个数 $n$ 与布尔函数 `expr_fn`，枚举所有真值指派并输出结果；并用它验证德摩根律 $\neg(p \wedge q) \equiv \neg p \vee \neg q$ 对所有指派成立。

---

**答案**: 参考实现（与正文编程任务一致）：

```python
import itertools

def truth_table(n_vars, expr_fn):
    """为 n_vars 个变量的布尔函数生成真值表。"""
    headers = [f"p{i}" for i in range(n_vars)]
    print(" | ".join(headers + ["result"]))
    print("-" * (len(headers) * 4 + 10))
    for vals in itertools.product([False, True], repeat=n_vars):
        result = expr_fn(*vals)
        row = [str(v)[0] for v in vals] + [str(result)[0]]
        print(" | ".join(f"{r:>2}" for r in row))

# 德摩根律验证：对全部 4 组指派恒为 True
truth_table(2, lambda p, q: (not (p and q)) == ((not p) or (not q)))
```

评分点：用 `itertools.product(..., repeat=n)` 枚举 $2^n$ 个指派（4 分）；函数接收布尔函数并逐行输出（3 分）；验证式写成等值判断且四行全为 True（3 分）。

**解析**: 真值表有 $2^n$ 行，是命题逻辑验证逻辑等价的基本手段；本题也可不用 itertools，用二进制计数递归枚举，等价实现同样给分。

**来源**: 01. 离散数学 §命题逻辑（编程任务 1）

### 23. 🟠【L3 应用】用 Python `threading` 复现一个竞态条件：两个线程各对共享计数器执行 10 万次 `+= 1`，观察丢失的更新；再用锁修复，并解释为什么无锁版本结果会偏小。

---

**答案**: 参考实现（对应正文编程任务 1、2）：

```python
import threading

N = 100_000
counter_buggy = 0

def increment(n):
    global counter_buggy
    for _ in range(n):
        counter_buggy += 1  # 非原子：读-改-写三步，线程切换会丢更新

t1 = threading.Thread(target=increment, args=(N,))
t2 = threading.Thread(target=increment, args=(N,))
t1.start(); t2.start(); t1.join(); t2.join()
print("无锁结果:", counter_buggy, "期望:", 2 * N)  # 通常小于 200000

# 加锁修复
counter_locked = 0
lock = threading.Lock()

def increment_locked(n):
    global counter_locked
    for _ in range(n):
        with lock:          # 临界区一次只进一个线程
            counter_locked += 1

t1 = threading.Thread(target=increment_locked, args=(N,))
t2 = threading.Thread(target=increment_locked, args=(N,))
t1.start(); t2.start(); t1.join(); t2.join()
print("加锁结果:", counter_locked)  # 恰为 200000
```

评分点：两线程各 N 次、无 `join` 漏写扣 2 分（4 分）；无锁版复现出小于 $2N$ 的结果并说明 `+=` 是“读-改-写”三步、切换交错导致两次递增读到同一旧值（3 分）；`with lock` 包住临界区后结果严格等于 $2N$（3 分）。

**解析**: `+=` 在字节码层面不是原子操作；这正是同步原语存在的理由。进一步的无锁方案可用 `threading` 不直接暴露的 CAS 循环实现，思想见 §无锁与无等待数据结构。
